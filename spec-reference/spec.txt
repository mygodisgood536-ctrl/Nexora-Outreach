
NEXORA OUTREACH
Full Product Vision, Architecture & Cline Implementation Instructions
AI-powered prospecting and outreach, on autopilot.
1. Purpose
This document is the implementation source of truth for building Nexora Outreach. Cline must use it as the product and engineering specification. The goal is not a simple lead generator or email sender. The goal is an autonomous prospecting and outreach platform that discovers relevant business opportunities, investigates them, analyzes websites or online presence, qualifies prospects, generates individualized outreach, sends messages through the user's authorized mailbox, monitors conversations, follows up when appropriate, and immediately notifies the user when a prospect replies.
The application must be a real production system with persistent backend jobs, scheduling, queues, secure authentication, OpenCode integration, email authorization, auditability, recovery, and a responsive UI.
2. Product Identity
Product: Nexora Outreach
Short description: AI-powered prospecting and outreach, on autopilot.
Primary purpose: Find opportunities, investigate them, personalize outreach, manage follow-ups, and surface replies with minimal manual work.
Initial example: a website designer finding businesses that need a new or improved website.
Long-term purpose: support many services and markets without rebuilding the product.

4. The Product Must Not Be Locked to One Niche
Do not hard-code Nexora as a restaurant finder or website redesign tool. Website redesign for restaurants is the first concrete use case. The user must be able to change what they are scouting for and who they are scouting.
Website designer: businesses with outdated, broken, weak, or missing websites.
Email marketer: businesses with opportunities for email marketing/customer retention.
SEO specialist: businesses with potential local/search visibility opportunities.
Social media service: businesses with weak or inactive social presence.
Graphic designer: businesses with branding/visual communication opportunities.
The user can describe the objective in natural language. Nexora should interpret that objective and adapt discovery, research, qualification, and outreach accordingly.
5. Account Creation and Login
5.1 Sign-up
Full name
Unique username
Security question
Security answer
When a username is entered, check availability immediately. If already used, require a different username. Enforce uniqueness server-side as well as in the UI.
5.2 Login
The requested login flow uses username plus the account's security question/answer credential. The answer must never be stored in plain text. Store a secure one-way hash using an appropriate password/KDF approach.
5.3 Security
Server-side credential validation.
Rate limiting and progressive lockout for repeated failed attempts.
Secure sessions with expiration and revocation.
Encrypted storage for sensitive email authorization tokens.
A safe account recovery mechanism; do not rely only on a guessable security question.
Audit important account and automation events.
6. User Email Account
The user must connect the mailbox Nexora will use to send outreach and monitor replies. Nexora must not ask the user to type their normal email password into Nexora. Use OAuth/API authorization where supported.
Initial connection targets: Gmail/Google Workspace and Microsoft/Outlook.
Send outreach.
Read incoming replies with minimum required authorization.
Detect replies.
Run follow-ups.
Disconnect/reconnect mailbox.
Pause sending.
Show connection status.
Keep email integrations behind a provider abstraction so more providers can be added later.
No email provider can guarantee inbox placement. Deliverability depends on domain authentication, reputation, volume, bounces, complaints, message quality, recipient engagement, and provider rules. Nexora must provide safe sending controls instead of promising spam-free delivery.
7. OpenCode Is the AI Provider/Model Layer
OpenCode must be installed, implemented, and integrated into the platform as the central AI provider/model runtime. Do not separately hard-code integrations for every provider and model.
NEXORA OUTREACH
      ↓
Central AI Runtime
      ↓
OpenCode adapter/integration
      ↓
Selected provider + selected model
      ↓
AI execution
Provider/model discovery must come from the OpenCode integration rather than a permanent hard-coded Nexora list.
The user can select a provider and model exposed by OpenCode.
The selected configuration is persisted safely.
Backend AI workers use the selected configuration.
New provider/model availability from OpenCode should be reflected without building a separate Nexora integration for every provider.
Never expose provider credentials unnecessarily to the browser.
Create one internal AI Runtime interface. Nexora business logic should call this interface. The OpenCode adapter handles provider/model resolution, execution, streaming where useful, structured outputs, errors, retries, and runtime diagnostics.
AI should handle reasoning tasks such as research interpretation, website/design assessment, qualification, personalized writing, and reply interpretation. Deterministic backend code should handle scheduling, queues, database state, sending limits, OAuth, email transport, notifications, retries, deduplication, and audit logs.

15. Personalized Outreach
Every qualified prospect must receive an individualized message based on actual research. Do not use a mass template with only the business name changed.
The user provides instructions about tone and content. Nexora writes and arranges the final message.
Example user instruction:
Write short, friendly, natural outreach.
Do not sound like a generic sales pitch.
Mention something specific that was actually observed.
Offer to improve/redesign the website first without upfront payment.
If they like the result, they can decide what they think the work is worth.
Do not make false claims.
Keep it easy to read.
Different prospect, different message.
Avoid repetitive openings and sentence structures.
Avoid generic corporate filler.
Do not fake personalization.
Do not claim to have observed something that was not observed.
Do not intentionally misrepresent an automated system as a human.
Avoid decorative separators or formatting the user does not want.
Keep messages short unless the mission says otherwise.
16. Free-First Website Offer
For the current website-design mission, the user wants to offer the redesign/improvement without requesting upfront payment. If the prospect likes the result, the prospect can decide what they believe the work is worth and pay accordingly.
This must be a configurable mission instruction, not a universal hard-coded business rule. Nexora should decide whether the opportunity calls for a full redesign, homepage improvement, mobile improvement, or another appropriate service.

Prevent duplicate outreach.
Maintain suppression records.
Honor opt-outs.

30. Error Handling and Recovery
Persist meaningful job state.
Retry transient failures with bounded backoff.
Do not retry permanent failures indefinitely.
Recover queued jobs after restart.
Avoid duplicate emails after uncertain send outcomes using provider IDs/idempotency where available.
Record AI generation failures and allow regeneration.
Separate browser failures, AI failures, email failures, and qualification failures.
Show user-friendly errors.
Keep detailed developer logs.

40. Definition of Done
Nexora Outreach is complete only when a real user can create an account, connect a mailbox, create a natural-language scouting mission, select service/targets/countries/schedule, activate it, and have the backend autonomously discover and investigate prospects, qualify them, generate individualized outreach, send it, monitor replies, notify the user, and perform configured follow-ups. The system must recover from restart/failure, prevent duplicate or suppressed outreach, and use OpenCode as the central provider/model runtime.
41. Final Instruction to Cline
Treat this document as the product vision and implementation contract. First inspect the existing repository and architecture. Reuse sound existing components where appropriate. Then implement the real working system in dependency order. Do not stop at a plan, UI prototype, fake integration, or simulated workflow.
Where an external service requires credentials or user authorization, build the real integration boundary and setup flow. Where a capability depends on an external provider, do not invent unsupported behavior. Where OpenCode's exact installed commands/configuration differ from assumptions, inspect the actual installed runtime and implement against the real interface.
Before declaring completion, run relevant tests and verify the real autonomous scheduler, worker recovery, OpenCode execution, mailbox connection, message lifecycle, reply detection, follow-up lifecycle, suppression, and pause controls. The final product must be Nexora Outreach: an autonomous prospecting and outreach platform, not merely a demonstration.
